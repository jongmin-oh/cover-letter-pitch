# cover-letter-pitch — 맞춤형 자기소개서 작성 스킬

JD(채용공고)와 본인 경험을 입력하면, **정해진 4블록 패턴으로 한국어 자기소개서**를 작성하는 Claude / Claude Code 스킬입니다.

```
1. 내가 할 수 있는 것 3가지   — JD와 직접 연결된, 내가 잘 할 수 있는 일
2. 내가 줄 수 있는 것 3가지   — 나를 뽑으면 조직이 얻게 되는 것
3. 솔직한 단점                — JD 대비 부족한 점 하나 + 극복 방법
4. 마지막 멘트                — 조직의 어느 부분에 기여하고 싶은지
```

블록의 순서와 내용은 고정입니다. 네 블록을 합쳐 **A4 한 장** 분량으로 씁니다.

> **이 4블록은 내용을 설계하는 틀이지 제출 문서의 목차가 아닙니다.** 완성본은 블록 이름도, 번호 목록도 없는 — 채용 담당자가 읽는 평범한 자기소개서 형태로 나옵니다. 지원서 양식에 그대로 붙여넣을 수 있습니다.

합격을 보장하거나 합격률을 예측하지는 않습니다.

## 두 가지 기준

- **가독성** — 비개발자도 한 번에 읽히는 문장. 한 문장에 한 가지만 담고, 전문용어는 그 기술이 하던 역할로 풀어 씁니다.
- **JD 직접 연관성** — 본문의 모든 내용이 JD의 특정 요구·업무·과제와 연결됩니다. JD와 짝지을 수 없는 내용은 좋은 경험이라도 넣지 않습니다.

두 기준 사이에 우선순위는 없습니다.

## 사실관계는 다루지 않습니다

자기소개서는 증명 문서가 아니라 제안서입니다. 사실 확인은 이력서, 포트폴리오, 면접에서 이뤄집니다. 그래서 이 스킬은 수치의 출처를 캐묻거나, 개인/팀 성과의 경계를 따지거나, 주장-근거 대조표를 만들지 않습니다. **근거가 약하다는 이유로 문장을 유보적으로 만들지 않고, 자신 있게 단정해서 씁니다.**

## 무엇을 하나

```
JD 입력 + 후보자 경험
  └─► JD 분석 (핵심 업무 / 요구 역량 / 조직의 과제 / 일하는 방식)
        └─► JD 항목을 먼저 세우고, 거기에 맞는 경험을 이력서에서 매칭
              └─► 4블록 골격으로 초안 작성 → 자소서 형태의 문단으로 변환
                    └─► 통과 게이트 7개 (Pass/Fail)
                          └─► 평가표 5항목 채점 (25점 만점)
                                ├─ 미달 → 최저 항목부터 수정 → 게이트로 복귀 (최대 3회)
                                └─ 통과 → 최종본 제공
```

- **JD 우선**: 이력서에서 자랑거리를 먼저 고르지 않고, JD 항목을 세운 뒤 거기에 맞는 경험을 찾습니다
- **고정 골격**: `할 수 있는 것 → 줄 수 있는 것 → 솔직한 단점 → 마지막 멘트` (설계용 틀)
- **제출 형태 분리**: 완성본은 블록 이름·번호 목록·개조식 없이 문단으로 흐르는 자기소개서로 출력합니다
- **단정형 문체**: 1·2번 블록에서는 유보 표현을 쓰지 않습니다. 유보는 3번 블록 한 번뿐입니다
- **번역**: 1번의 "내가 하는 일"을 2번에서 "조직이 얻는 것"으로 바꿔 씁니다 — 같은 말의 반복이 아닙니다
- **자체 평가 루프**: 초안을 그대로 내보내지 않고, 기준을 통과할 때까지 스스로 채점하고 고쳐 씁니다
- **최소 질문**: 자료에서 알 수 있는 내용은 다시 묻지 않습니다

## 설치

두 가지 방법 중 하나를 고르세요. **방법 1(스킬 디렉터리 클론)이 가장 간단**합니다.

### 방법 1 — 스킬 디렉터리에 클론 (권장)

레포를 스킬 폴더로 바로 클론합니다. 전역으로 쓰려면 `~/.claude/skills/` 아래에, 특정 프로젝트에만 쓰려면 그 프로젝트의 `.claude/skills/` 아래에 둡니다.

```bash
# 전역 설치 (모든 프로젝트에서 사용)
git clone https://github.com/jongmin-oh/cover-letter-pitch ~/.claude/skills/cover-letter-pitch

# 또는 특정 프로젝트에만
git clone https://github.com/jongmin-oh/cover-letter-pitch .claude/skills/cover-letter-pitch
```

다음 세션부터 자동 로드됩니다. `/cover-letter-pitch` 로 호출하거나, 그냥 "이 JD로 자기소개서 써줘"라고 요청하면 description 트리거로 자동 호출됩니다.

### 방법 2 — 플러그인으로 로컬 테스트

레포에 `.claude-plugin/plugin.json` 매니페스트가 있어 플러그인으로도 로드됩니다. 설치 없이 바로 띄워 테스트할 때 유용합니다.

```bash
# 레포를 클론한 위치에서
claude --plugin-dir /path/to/cover-letter-pitch
```

플러그인으로 로드하면 스킬이 네임스페이스로 호출됩니다 — `/cover-letter-pitch:cover-letter-pitch`. (정확한 이름은 `/help`에서 확인 가능합니다.)

### Claude (claude.ai)

`SKILL.md`를 커스텀 스킬/프로젝트 지침으로 등록하면 동일하게 동작합니다.

## 사용법

호출 시 다음 자료가 필요합니다.

**필수**
- JD 전문 (텍스트 / 파일 경로 / URL)
- 이력서 (파일 경로 또는 붙여넣은 텍스트)

**있으면 더 좋음**
- 포트폴리오 (PDF 파일 / 웹 링크 / 이미지 / 텍스트)
- 지원서 문항 (자유 양식 / 문항형)
- 글자 수·분량 제한
- 회사·제품 정보 (회사명, 제품, 최근 방향)

### 예시 프롬프트

```
아래 JD로 자기소개서를 써줘. 이력서는 resume.pdf, 포트폴리오는 https://my.portfolio 참고.
지원서 문항: 자유 양식 / 글자 수 제한: 2000자

[JD 전문]
...
```

## 기본 작성 기준

사용자가 지정한 문항과 분량이 항상 우선합니다.

- **기본 분량은 A4 한 장** — 인쇄했을 때 한 페이지에 들어가는 길이
- **글자 수**: 공백 포함 1,800~2,200자
- **분량 배분**: 1번 약 40%, 2번 약 35%, 3·4번 약 25%
- **넘치거나 모자랄 때**: 블록을 빼거나 항목을 늘리지 않고, 각 항목의 문장 수로 맞춥니다
- **제한이 A4 한 장보다 짧을 때**: 1·2번 블록의 항목을 3개에서 2개로 줄입니다
- **문항형 지원서**: 문항을 우선하되, 각 답변 안에서 `JD 연결 → 할 수 있는 일 → 조직이 얻는 것` 순서를 유지합니다
- **문체**: 볼드로 논지를 세우고, 기술명은 그 기술이 하던 역할로 풀어 쓰고, 숫자는 주장 뒤 근거 자리에

### 완성본 문단 배치

| 문단 | 담는 블록 |
|---|---|
| 1~3 | 할 수 있는 것 3가지 — 한 문단에 하나씩 |
| 4~5 | 줄 수 있는 것 3가지 — 주어가 조직으로 바뀌는 지점 |
| 6 | 솔직히 부족한 점 → 극복 |
| 7 | 기여 선언 1~2문장 |

블록 이름은 소제목으로 쓰지 않고, 문단 사이는 전환 문장으로 잇습니다. 소제목이 허용되는 양식이면 블록 이름 대신 그 문단의 핵심 주장을 소제목으로 씁니다.

### 블록별 규칙 요약

**1. 내가 할 수 있는 것 3가지**
- JD에 없는 능력은 아무리 강점이어도 넣지 않습니다
- 각 항목: `할 수 있는 일 선언(볼드) → 그렇게 말하는 이유 → 이 회사에서의 모습`
- "해본 적은 있습니다", "부족하지만" 같은 유보를 붙이지 않습니다
- 기술명 나열이 아니라 할 수 있는 **일**로 씁니다

**2. 내가 줄 수 있는 것 3가지**
- 주어가 나에서 조직으로 바뀝니다 — 사람이 아니라 결과를 씁니다
- 1번을 문장만 바꿔 반복하지 않고, 능력을 조직의 이득으로 번역합니다
- "열심히 하겠습니다" 같은 다짐은 줄 수 있는 것이 아닙니다

**3. 솔직한 단점**
- JD 요구 중 부족한 항목 **하나**만, 에두르지 않고 인정합니다
- 지원 자체가 무의미해지는 핵심 요구는 고르지 않습니다
- "꼼꼼해서 속도가 느립니다" 같은 위장된 자랑은 쓰지 않습니다
- 극복은 의지가 아니라 방법으로 씁니다. 마지막은 반드시 극복 문장입니다

**4. 마지막 멘트**
- JD에서 읽은 조직의 과제를 지목하고, 거기에 기여하겠다고 선언합니다
- "기회를 주신다면", "최선을 다하겠습니다" 같은 수동적 표현은 쓰지 않습니다
- 앞 블록을 요약하지 않고, 기여하고 싶은 지점 하나로 닫습니다

## 평가 기준과 수정 루프

초안을 그대로 내보내지 않습니다. 아래 기준을 통과할 때까지 스스로 채점하고 고쳐 쓴 뒤, 최종본만 보여줍니다. 중간 버전은 출력하지 않습니다.

**① 통과 게이트 (하나라도 Fail이면 채점 없이 수정)**

| # | 게이트 | Fail 조건 |
|---|---|---|
| G1 | 블록 구성 | 네 블록이 순서대로 있지 않음 |
| G2 | 항목 수 | 1번 또는 2번이 3가지를 못 채움 |
| G3 | 단정 | 1·2번에 "부족하지만", "~인 것 같습니다" 같은 유보 표현이 있음 |
| G4 | JD 범위 | JD에 없는 능력·성과가 들어감 |
| G5 | 단점 | 단점이 둘 이상이거나, 장점으로 뒤집혔거나, 극복 문장으로 안 끝남 |
| G6 | 마무리 | 기여 선언으로 끝나지 않거나 "기회를 주신다면"이 들어감 |
| G7 | 분량 | A4 한 장 또는 지정 글자 수를 벗어남 |
| G8 | 제출 형태 | 블록 이름이 소제목으로 남았거나 번호 목록·개조식으로 쓰임 |

**② 평가표 (각 5점, 총 25점)**

| 항목 | 무엇을 보는가 |
|---|---|
| E1. JD 직접 연관성 | 모든 항목이 JD의 특정 문구·업무와 1:1로 짝지어지는가 |
| E2. 가독성 | 비개발자가 한 번 읽고 각 항목의 뜻을 말할 수 있는가 |
| E3. 1번 블록의 힘 | 세 항목이 서로 다른 요구를 맡고, 단정과 근거가 함께 있는가 |
| E4. 2번 블록의 번역 | 주어가 조직이고, 1번의 반복이 아닌가 |
| E5. 대체 불가능성 | 회사명과 포지션을 바꾸면 문장이 성립하지 않는가 |

**③ 완성 조건: 총점 21점 이상 + 모든 항목 4점 이상**

미달이면 가장 낮은 항목부터 수정하고 게이트로 돌아갑니다. 이미 4점 이상인 항목은 건드리지 않고, 같은 항목이 두 번 연속 미달이면 문장이 아니라 **소재를 교체**합니다. 최대 3회까지 돌고, 그래도 미달이면 최종본과 함께 미달 항목·원인을 알리고 필요한 경우 표적 질문을 1~3개 덧붙입니다.

## 출력

제출용 본문을 먼저 채팅에 제공합니다. 지원서에 그대로 붙여넣을 수 있는 자기소개서 형태이며, 작업용 라벨은 함께 출력하지 않습니다. 사용자가 파일 저장을 요청하면 `cover-letters/{회사명}-{포지션}.md`에 저장합니다.

본문과 함께 글자 수, 자체 평가 총점(예: `24/25`), 적용한 가정을 짧게 덧붙입니다.

저장 파일에는 제출용 본문만 포함합니다. JD 분석 같은 내부 자료도 요청한 경우에는 `{회사명}-{포지션}-notes.md`로 분리합니다.

## 핵심 원칙

- 네 블록은 내용 설계용 — 완성본은 담당자가 읽는 자기소개서 형태로 내보낸다
- 초안을 그대로 내보내지 않는다 — 게이트와 평가표를 통과할 때까지 고쳐 쓴다
- JD와 짝지을 수 없는 내용은 이력서에 남겨두고 자기소개서에서는 뺀다
- 할 수 있다고 쓸 때는 유보 없이 단정한다 — 유보는 3번 블록 한 번뿐
- 단점은 하나만, 솔직하게, 극복 방법과 함께 쓴다
- 마지막 문장은 조직에 기여하고 싶은 지점 선언으로 끝낸다
- 사실 검증, 수치 출처 확인, 실패 서술을 요구하지 않는다
- "성실하고 열정적인"류의 빈 형용사보다 이를 증명하는 행동을 쓴다
- 회사의 상황을 단정하지 않는다 — 공고에 단서가 있을 때만 해석한다
- 사용자가 요구한 형식과 분량을 기본값보다 우선한다
